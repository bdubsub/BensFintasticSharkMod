## Purpose and Ownership

This phase turns the retained 0.23 feature set into a proven regression baseline for release 0.24. It canonically owns `BFS-REQ-001` through `BFS-REQ-012`: shared shark locomotion, bite approach and contact, Tiger Shark item curiosity, Oceanic Whitetip grab and Blacktip Reef latch cleanup, `/bfs info` and habitat accuracy, Prismarine armor swimming fit, the supplied Oceanic Whitetip state mapping, Atlantic Cod and Atlantic Salmon including the `Spin` name behavior, their items and acquisition paths, vanilla aquatic controls, the emergency population invariant, Shark Spotter, and the four Atlantic fish advancements.

The master plan owns product scope, stable requirement wording, phase topology, source precedence, and the plan wide Definition of Done. This file owns only dependency ordered implementation and evidence for `BFS-PHASE-001`. It may refine test procedure without weakening or expanding the master contract. If execution discovers a conflict with the master, a material owner decision, or work outside the registered requirements, stop with `PLAN_REVISION_REQUIRED`; do not edit the master from this phase.

The boundary with `BFS-PHASE-002` is deliberate. This phase must prove the retained shared movement contract and Tiger item curiosity, and it must repair any drift in those retained paths. It does not close the newer Tiger combat and animation requirements `BFS-REQ-017` through `BFS-REQ-019` or beta defects `DEF-024-002` through `DEF-024-004`. Phase 002 consumes the stable movement, attack timing, animation state, and cleanup contracts produced here. A retained contract failure may not be deferred merely because a later phase also touches the same entity.

## Architecture and Implementation Boundaries

### State authority and data flow

The logical server owns path decisions, curiosity selection and timeout, target priority, bite scheduling and damage, grab and latch state, passenger lists, replacement, spawn filtering, loot, fishing results, and advancement criteria. Synchronized entity data and normal entity packets carry presentation state to clients. Client renderers, GeckoLib controllers, armor models, and `GrabClientHandler` may present authoritative state but may not originate damage, replacement, passenger truth, or persistent gameplay state.

Shared shark behavior flows from SmartBrainLib activities and memories through `AbstractSharkEntity`, `SharkSwimmingMoveControl`, navigation, and species hooks. Preserve this dependency direction. A species override may refine physical reach, animation impact delay, or a species specific temporary behavior. It must not duplicate the shared scheduler or create a second authority for pathing and attack state.

Tiger curiosity is a transient state machine. Item eligibility leads to one item identity and one submerged intercept. Server ticks validate the item, timer, path, flee state, and target priority. A cosmetic bite produces presentation only. Every terminal transition clears the same memories and navigation state before cooldown and ordinary behavior resume. Do not persist a floating item reference or introduce a save migration for this temporary state.

Grab and latch use entity passenger relationships and synchronized timers. Server release is the source of truth; client camera and animation derive from rider state. All removal and connection lifecycle hooks must converge on one idempotent cleanup operation so repeated cleanup is harmless.

### Registration, configuration, and generated data

Stable public identifiers remain `bensfintasticsharks:atlantic_cod`, `bensfintasticsharks:atlantic_salmon`, their retained item and advancement IDs, and existing Prismarine and Oceanic identifiers. Preserve save compatibility and unknown NBT. Spawn egg conversion copies only safe entity data supported by the current event path; never trust spawn egg data to replace entity type, bypass permissions, or install arbitrary passenger state.

`BfsConfig` owns common defaults and documented restart behavior. Runtime cap overrides in `MobCapManager` are a separate server lifetime feature and must not imply that replacement or suppression changes are safely live reloadable. Replacement policy remains exact namespace and path matching, then resolves through registered entity types. Replacement precedes suppression. Category parity is checked both at common setup and at the spawn boundary, and failure cancels the attempt before adding an entity.

Forge data providers are authoritative for generated biome tags, biome modifiers, item models, loot tables, recipes, loot modifiers, language, and advancements. Change provider source first, run `./gradlew :forge:Data`, and inspect generated additions, removals, and unrelated churn. Hand edited generated JSON is not an acceptable durable fix.

### Client and dedicated server separation

All `net.minecraft.client` types, GeckoLib renderers, armor rendering, camera manipulation, and visual capture logic remain under Forge client initialization or client packages. Common entities may expose synchronized values and animation relevant predicates without loading renderer classes. `./gradlew :forge:Server` must prove no common initialization path loads client classes.

The Prismarine geometry change must preserve vanilla player limbs. The armor model follows player pose continuously rather than switching between a few disconnected clearance states. Oceanic and fish controllers select states from synchronized or directly observable entity state; server damage and release behavior do not wait on client animation completion.

### Concurrency, lifecycle, and performance

Entity mutation occurs on the logical server thread. The existing replacement reentry guard must prevent recursive spawn event replacement and be cleared in a `finally` path. Once only category error reporting must remain thread safe and avoid log spam. Runtime cap maps may remain concurrent where existing commands can change them during server operation.

Do not add full world entity scans, filesystem access, blocking operations, or per tick logging. Curiosity item scans and cap counts remain bounded in radius and cadence. Population tests may instrument counts in test code or external evidence capture, not by shipping noisy per tick production logging.

### Compatibility and migration

No data migration is expected because retained identifiers and save formats are preserved. Validate an existing 0.23 world copy with Atlantic fish, custom named Salmon, sharks, Prismarine equipment, and advancement progress. Back up the world before runtime recovery rehearsal. A load failure, lost custom name, changed variant, missing equipment, orphaned passenger, or advancement parse error blocks completion.

Existing excess Atlantic fish are not deleted. The corrective behavior is forward acting: new spawn attempts obey category and one for one limits, while existing fish use inherited despawn behavior. Operator documentation must distinguish optional config changes from destructive cleanup and require restart for the relevant spawn controls.
