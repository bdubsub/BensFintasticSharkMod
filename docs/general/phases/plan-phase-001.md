## Purpose and Ownership

This phase delivers one server owned, session only effective settings service and routes it through every current BFS species movement, spawning, scale, attribute, behavior and recovery consumer. It replaces fixed hidden vertical ratios and repeated attribute multiplication with an explicit revisioned contract, then makes shark motion safe for the whole scaled and pitched body. It does not select subjective balances. The operator changes values manually, reads their effective source and revision, and resets them without writing a profile or TOML.

The master retains product scope, shared interface signatures, default bounds, cross phase topology, acceptance authority, and endpoint authority. This file owns the executable detail for this one phase only. `BFS2-REQ-007` remains owned by Phase 003. This phase supplies the generic settings catalog entries and capability representation which Phase 003 will consume for disturbance fields. It does not add disturbance producers, eligibility decisions, boat interest, alerts, or their assertions.

### Independent movement oracle

P001-TASK-002 owns this oracle; P001-TASK-004 supplies its bounded capture before final evidence. For each of the 22 registry entries, exercise the actual adapter and final travel path in sufficiently large source water with no arrival braking, obstacles, currents, gravity contribution, or external impulse in the measured powered component. Apply the direction at the adapter's intent input, never assign final velocity. Match initial conditions, normalized intent and active state between paired runs. Use `(2,6)`, `(6,6)`, and `(6,2)` for base axis pairs. For sprint pairs hold the bases fixed, change `(Mh,Mv)` from `(1,1)` to `(1.2,1)`, then to `(1.2,1.5)` in pursuit or flee. Repeat the same multipliers in cruise to prove they are inactive. These are fixture values, not balance defaults.

The test independently calculates each expected powered step from recorded normalized input `d`, state, bases and multipliers using IFC-003. It must not call the production velocity helper or derive its expected value from the emitted requested velocity. For example, `d=(3/5,4/5,0)` in cruise gives expected blocks per tick `(0.06,0.24,0)`, `(0.18,0.24,0)`, and `(0.18,0.08,0)` for the three base pairs. The first pair preserves vertical motion and the second preserves horizontal motion. Include both vertical signs and horizontal headings. Zero intent is tested separately and never used as evidence that a nonzero coefficient reaches a consumer.

Configure the fixture's acceleration to 80 blocks per simulation second squared, turn and pitch rates to 360 degrees per simulation second, and pitch limit to 80 degrees so the listed unobstructed pairs can settle without introducing a hidden limit. After each change, allow 100 simulation ticks outside the measurement capture and verify the requested intent, state, settings revision and final writer have settled. Then start a fresh 200 tick capture for at most eight targets, with the fixture automatically aligning its 200 consecutive measurement ticks to the first captured server tick. Preserve the initial and final positions, powered displacement, separately measured external displacement, normalized input, effective values, writer count and exact tick boundaries. Use per tick detail only within this IFC-001 high detail window. Run additional batches to cover all 22 entries.

For each Cartesian component, compare `20 * sum(actual powered steps) / 200` with `20 * sum(independently expected steps) / 200`, in blocks per simulation second. Each error must be at most 0.05. Under matched input and state, the component unaffected by the changed coefficient must also differ by at most 0.05 between runs. Require one final writer on every measured tick. A changed intent/state, unsettled acceleration or turn, arrival reduction, safety restriction, external displacement that cannot be separated, or incomplete recording invalidates this unrestricted fixture; it must not be hidden by omitting inconvenient samples. Separate real pursuit/flee and blocked terrain fixtures verify natural state selection, declared limiting reasons, and external physics. Minimum acceleration and other extreme settings retain their own finite and constrained motion tests rather than inheriting this fixture's settling assumption.

## Architecture and Implementation Boundaries

The logical server is authoritative. `BfsCommands` and `BfsDebugCommands` parse only into IFC 002 transactions. A specialized command delegates to the same transaction as `set`, so there is no second override store. The resolver supplies one immutable snapshot to movement adapters, natural spawn gates, scale adapters, attributes and `SpeciesBehaviorEngine`. Clients receive only the state necessary for existing presentation and local diagnostics. Client classes remain Forge client side and cannot be loaded on a dedicated server.

The catalog uses master bounds and units. Values are finite and sorted before mutation. The `*` target expands only the sorted current BFS registry. Mandatory movement, sprint, group and scale fields cannot be unavailable. A nonuniversal supported attribute or behavior field returns `supported`, `read_only`, or `not_applicable` with a concrete reason. A wildcard containing an unsupported field rejects with sorted species and fields before changing any target. A version mismatch rejects with its expected and observed revision. No mutation changes TOML, writes named profiles, or grants a player privilege.

Scale is a finite value in `[0.25,2]` calculated from a persisted normalized roll. The common `BfsAquaticEntity` implementation is not treated as universal. Explicit adapters cover all noninheriting SmartWaterAnimal, stingray, seal and Atlantic fish paths. `getDimensions`, eye position, renderer scale and IFC 003 envelope all consume the same effective scale. A live scale mutation requires a conservative fit check for the existing full body envelope. Failure rejects the whole transaction as `BODY_NO_FIT`, preserving old revision, dimensions and health.

Natural spawn quantity is consumed at `MobCapManager.onFinalizeSpawn`, `spawnGroupExtras` and the actual placement or admission gates exposed by `BfsSpawnPlacements`. It remains subject to chance, cap, local cap, spacing, habitat and collision. Administrative summon and spawn egg paths are explicitly one requested entity and do not use natural group expansion. Reset changes future resolution only and never deletes or creates existing mobs.

Attributes use immutable base definitions and stable named owned modifiers, or an equivalent absolute recomputation that can identify and replace only its own contribution. Attribute writes preserve the prechange health fraction after a valid maximum health change, do not restore full health, and leave foreign modifiers intact. They run only at explicit lifecycle and revision application points, never from a per tick parser. The recovery, hunting, sensing and cooldown consumers read the same revision and preserve existing permission, team, range, line of sight and chunk loading behavior.

One adapter selects the IFC 003 powered vector before turn, acceleration, collision and safety constraints. The output record distinguishes desired horizontal and vertical blocks per simulation second from actual constrained velocity, and distinguishes simulation ticks from wall time. No postcollision vertical impulse, speed floor or route cap may silently replace a requested coefficient. Safety can limit axes only through the envelope evaluator and must report its reason. The evaluator samples a swept scaled body and fin representation over the proposed pose and requires wet body and solid clearance. During this phase the dorsal fin is also wet. The reserved future `boat_track` medium policy may permit only a dorsal fin surface crossing while keeping the body submerged and every part solid clear. It does not use per tick mesh inspection, center only water tests, teleporting or arbitrary reorientation. Bounded recovery brakes, finds a safe wet pose through existing route mechanisms and returns ordinary behavior after configured attempts. A repeated failure has a terminal reported reason rather than an endless loop.
